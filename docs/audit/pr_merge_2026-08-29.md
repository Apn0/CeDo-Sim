# Batch PR merge audit — 2026-08-29

Ten bot-authored PRs (#153–#165) were open at once, four of them editing the same
file. GitHub reported **all ten** as `mergeable=true, mergeStateStatus=CLEAN`.

That report was correct and still misleading: GitHub computes each PR's
mergeability against `main` **independently**, as if the other nine did not
exist. Two of them merge cleanly and produce a file that does not compile.

This repo has **no CI** (`statusCheckRollup` is empty on every PR), so
"mergeable ✅" only ever meant *git can apply this patch*. Nothing had validated
any of the ten against `tools/regression/run.sh`, which is the only real gate.

| #153, #154, #155, #156, #157, #158, #162, #163 | **#161** (broken), **#166** (no-op) |

Net effect on the harness: **zero new failures**, measured by running the full

|---|---|---|

(The sweep file count is unchanged because these PRs append to existing test

## The defect this caught

PRs #155 and #158 each added a local named `shell` to `test_wall_openings.gd`'s
`_init()`. Separate hunks, so:

- `git merge` reported **no conflict**
- GitHub reported the PR as cleanly mergeable
- the merged file failed with
  `Parse Error: There is already a variable named "shell" declared in this scope.`

GDScript has no block scoping, and an unparseable test file stops the whole
harness at its parse gate (`run.sh:40`) — the documented catastrophic mode that
previously cost this project ~3 weeks (`_live_pieces`, see
`material_trace_2026-08-18.md`).

Reproduced deliberately on the real branch before fixing, so this is measured,
not inferred:

```
$ git merge origin/main          # no conflict, exit 0
$ sed -n 's/^\s*var \(\w*\).*/\1/p' src/tests/test_wall_openings.gd | sort | uniq -d
shell
$ godot --headless --path . --check-only --script res://src/tests/test_wall_openings.gd
SCRIPT ERROR: Parse Error: There is already a variable named "shell" declared in this scope.
```

Fix: PR #155's instance renamed to `mock_shell` on its own branch before merge.

**Pre-merge check for any batch touching one file twice:**

```bash
sed -n 's/^[[:space:]]*var \([A-Za-z_][A-Za-z0-9_]*\).*/\1/p' <file> | sort | uniq -d
```

## The finding that outlives this merge

**Eight of the ten PRs add tests the harness never runs.** `run.sh:261` iterates
an explicit allow-list of `.tscn` suites; everything else is seen only by the
full-tree parse sweep, which proves a file *parses* and nothing more.

So the merged coverage is, today, close to zero real protection. Wiring these
into the harness is separate, queued work — and each needs a `--quit-after`
guard plus an explicit `quit(1)` on failure paths, or a failing suite will hang
the run rather than fail it.

> **CLOSED 2026-08-30** for all five suites this batch produced —
> `test_wall_openings`, `test_push_gate`, `test_texture_cache`, `test_walkie`
> and `test_tool_placement_mode` are now executed by `run.sh`. See
> `docs/audit/harness_wiring_2026-08-30.md`. The prescription above was right:
> the hang was real, and it was measured on the way in rather than argued —
> the old bare-`assert()` form of `test_wall_openings.gd` with one claim broken
> ran for **90 s without exiting (`timeout` rc 124)**, while the counted form of
> the same file with the same claim broken exits **rc 1** with a red verdict.
>
> The finding's *general* half is still open and is much larger than this batch:
> **98 of 133 files in `src/tests/` are still executed by nothing.**
